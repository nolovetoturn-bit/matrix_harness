## 案例 1：RMS 价格洞察 V2.1.0 前端交付（p1 + p2）

### 拆解结果

```text
PB_交付(n, V2.1.0需求)
├─ PB_范围判定(n−1)                 ← p1 阶段1
│   ├─ Det: 读文档 / CSV转码 / 统计19条任务
│   ├─ gen(choose): 章节↔任务归类 → 覆盖矩阵
│   └─ gen: 批次划分
├─ PB_契约设计(n−1)                 ← p1 阶段2
│   ├─ Det: 原型 html 结构提取（字段/tab/筛选/弹窗）
│   └─ gen: 字段命名 / 类型 / 计算口径
└─ fold 页面 ∈ [映射管理, 看板, 明细]:
    └─ PB_页面(n−1, 页面)           ← p1 阶段3/5/6 + p2 全程
        ├─ gen: 规格提取（原型→实现规格）
        ├─ gen: 实现（Vue组件+路由+i18n）
        ├─ validate: 真实页 DOM 逐项断言 (Det)
        ├─ orElse: 修复回路（TDZ白屏 → repair → 重验）
        └─ PB_像素对齐(n−2, 页面)     ← p2 主体，跑了 3 遍
            ├─ Det: 截图管线（起服务/截图/裁剪/JPEG→PNG/视口对齐）
            ├─ choose: 方案选型（视口基准1600、headless vs 扩展截图）
            │          └─ orElse: 方案A(JPEG+视口漂移)失败 → 方案B(CDP)
            └─ loop: 测量 → diff_images → 归因 → 修CSS → 重截
                ├─ Det: 几何测量 + diff 数值
                ├─ gen(choose): 差异归因（CSS结构差 vs 字形/JPEG噪声）
                └─ gen: CSS 修复
                退出判据 (Det): tol 下残差全落在字形/编码区 → 收口
```

模型对照：human choose（“先做比价看板”）作为下一次调用的 Cin 注入；try/catch 消解为 orElse 修复回路；validate 全为 Det（DOM 断言 / diff 数值 / 探活 302）；截图管线与归因规则从手搓沉淀为脚本与规则——正是“确定性剥离”的活例（NDet 核单调收缩）。

## 案例 2：酒店清盘可见性排查（p3）

来源：`C:\Users\admin\Desktop\酒店清盘数据可见权限排查SQL.md`，对应日志条目 `20261023T140544-51c5`。与案例 1 同属 RMS，但性质是**线上故障排查**，不是交付。

### 拆解结果

```text
PB_排查(n, 现象: 用户看不到清盘数据)
├─ PB_前提证伪(n−1)              ← 先否掉"是权限问题"这个初始假设
│   ├─ Det: 扫全部分支查 dataFilterFlag / revenueAuthHotelIds
│   ├─ Det: 读 Mapper.listPage 硬条件（仅 cleared + is_deleted）
│   └─ gen: 区分"权限不可见" vs "数据真的没了"
├─ PB_历史追溯(n−1)              ← 用户纠偏："我记得这里改过权限"
│   ├─ Det: git 检索 f03c9feca / 2fbc65ba0 / a39aa7542
│   └─ gen(choose): 判定改动落在哪个模块 → 跟进，不在清盘
├─ PB_口径复算(n−1)              ← 先把"他本该看到什么"算出来
│   ├─ Det: 连 dev 库实跑 + 总数/有效/逻辑删除统计
│   ├─ Det: 修正实体（袁淦斌 → 袁淦彬，staff_id=798）
│   └─ gen: 设计可见性判定 CASE（收益维度 / 跟进关系 / 无关系）
└─ PB_现场验证(n−1, 人)          ← 最后一步靠人，模型自身无法完成
    ├─ await human: 用户在本机扫码登录 RMS，注入真实登录态
    ├─ Det: 复现空态 + 抓请求/控制台
    └─ gen: 归因 → 前端 catch 吞错渲染空态，并非无数据
```

### 关键点：第一个「挂起 / 恢复」实证

最后一步不是模型自己跑的——**让用户在本机扫码登录 RMS**，才拿到真实账号态去复现故障。按模型写法等价于：

```text
PB_现场验证(n−1, 人) = let ctx = await human(扫码登录注入) in PB_复现(n−2, ctx)
```

流程挂起 → 上下文封存 → 人完成外部动作 → 下一次调用把登录态作为 `Cin` 注入。这验证了"不建模 await、只用分次调用"的约定；同时确认**环境非确定性（生产版本 / 账号 / 数据状态）是第三类非确定源**，只能靠人注入确定值。

## 可抽取的复用 PB（案例 1）

| # | PB | 签名 | Det 占比 | 频次 | 抽取建议 |
|---|---|---|---|---|---|
| 1 | PB_像素对齐 | Nat → 页面×原型 → Maybe 收口结论 | ~80% | 每页 1 次，跨项目可用 | 最优先，固化为 skill/插件；gen 核仅剩归因+修CSS |
| 2 | PB_页面实现骶架 | Nat → 原型页 → Maybe Vue页面 | ~40% | 本项目复用 3 次 | 抽为模板：规格提取→组件生成→DOM断言→repair |
| 3 | PB_handoff 接力/生成 | Nat → 交接md → Maybe 进度状态 | ~70% | 每会话边界 2 次 | 近似模板：读交接→验环境→对齐进度 |
| 4 | PB_范围判定 | Nat → 需求×任务单 → Maybe 范围矩阵 | ~50% | 每版本 1 次 | 输出格式固定，gen 核为归类 |
| 5 | PB_契约设计 | Nat → 原型页 → Maybe 契约文档 | ~50% | 每大模块 1 次 | 与 #2 共用“原型规格提取”这个 Det 子函数 |

两个观察：
1. #1、#3 的 Det 部分占大头，再固化一至两轮后 gen 核会缩得很小——最值得先抽。
2. #2、#4、#5 共享同一个 Det 子函数（原型/文档结构化提取），抽取时应作为公共叶子，而非各抽各的。

## 待办 / 下一步

- **暂不立即做插件化**：等累积更多 case（建议 3–5 个完成开发周期的会话）后，再横向对比这些复盘，识别稳定不变的 PB 形态，再落成插件开发需求。
- 下次对比时的判断依据：同一 PB 在不同 case 中出现次数、签名是否一致、Det 子函数是否可复用同一实现、gen 核是否可归并。
- 待对比清单（现已 2 个 case）：
  - 案例 1：RMS 价格洞察 V2.1.0 前端交付（p1+p2）—— 交付型，`PB_交付` 树
  - 案例 2：酒店清盘可见性排查（p3）—— 排查型，`PB_排查` 树
  - 待补：其他项目/模块的完整周期会话（目标累计 3–5 个）
- 对比时重点看**跨类型共用的 Det 叶子**，而非顶层 PB：交付型与排查型看似不同，但共用了「代码/文档全量扫描找特征」「连库实跑+统计」「实体名/工号纠正」这些确定性子函数，这类叶子比顶层 PB 更容易抽成插件。
- 已出现的共性信号：两个案例都出现「人注入确定值」环节（案例 1 是选择页面顺序，案例 2 是扫码登录），说明 `await human` 的注入点是跨案例稳定需求。
