# 项目设计探索：从概率图灵机到能力演化

## 开篇

我们想回答的问题是：为什么一个 harness 加上 LLM 组成的 agent，能展现出远强于单次模型调用的能力？这个问题背后，是一个更深层的判断——**单纯的 LLM 不是图灵机，而 harness + LLM 组成的 agent 是。**本文从这个判断出发，逐步推导出一套关于 agent 如何被组织、如何被训练、能力如何沉淀的系统设计。

## 1. 概率图灵机

### 1.1 为什么说 LLM 不是图灵机，而 agent 是

图灵机之所以是图灵机，不在于它内部有多少参数、多少知识，而在于它具备完整的计算结构：有足够的持久状态，有根据当前状态和输入推进下一步的控制流，有明确的接受与拒绝条件。单次 LLM 调用缺少的正是这些。它根据有限上下文产生一个输出的概率分布，生成结束之后，状态与控制流就消失了。

harness 补齐了缺失的部分。它给模型装上循环，让输出能够继续驱动后续步骤；装上状态，让中间结果能够被保存下来；装上控制流和验收门禁，让整个过程有了明确的起点、推进规则和终止条件。

因此，**harness 与 LLM 结合之后，得到的不只是一个更强的语言模型，而是一台可以持续计算的机器。**这台机器在每一步都可能根据概率选择不同的走向，所以我们称它为概率图灵机。更准确地说，它不是一个单一的概率图灵机，而是一个概率图灵机族——不同的模型、不同的 harness 配置、不同的工具组合，构成一族不同的机器。

### 1.2 两种权重调整：隐式与显式

一旦把 agent 看作概率图灵机族，"训练"的含义就变得清晰了。**后训练和 harness，本质上都是在对这个概率图灵机族做权重调整。**它们的区别只在于调整什么、成果放在哪里。

后训练的调整对象是 LLM 本身。它直接改变模型的内部参数，从而改变每一步随机转移的概率分布。这是一次**隐式调整**：调整的成果被编码在参数里，模型换了或丢了，这些调整就随之而去，不一定能被单独拆出来、保存下来、复用起来。

harness 的调整对象是 agent。它不改变模型参数，而是改变这台机器怎么运行——哪些状态可见、哪些动作可用、什么时候重试、什么算完成。这是一次**显式调整**：调整的成果可以落到提示词、流程定义、记忆、契约、检查点这些看得见、能 diff、能回滚的东西里。

**这一个区别，是我们整套系统的出发点。**后训练把能力藏进参数这个黑箱里，harness 则把能力摆到工程产物上。前者难以遗传，后者可以。

### 1.3 概率图灵机的代价与威力

这里要正面说清楚概率图灵机的两副面孔。

第一副面孔是它的代价。确定性图灵机面对一个输入，给出一条确定的路径；概率图灵机给出的是一个可能性空间。要在这个空间里收敛出一个可靠的结果，就需要反复采样、反复验证。**换句话说，概率图灵机为了覆盖更多的可能性，付出了额外的计算效率。**这是它必须承受的成本：泛化越强，单次收敛越贵。

第二副面孔是它的威力。正是这个"可能性空间"，让概率图灵机族在解决问题时的泛化能力远高于确定性图灵机。确定性图灵机只能走被硬编码好的那一条路；概率图灵机却能在更广阔的空间里搜索，在需求不够精确、规格不够完备的任务上，仍然有办法给出可接受的结果。

**高效率但泛化弱的确定性机器，与低效率但泛化强的概率机器，构成一组真实的取舍。**我们的系统设计，就是围绕如何最大化利用后者的泛化能力、同时限制前者的成本展开的。

### 1.4 AGI 与 RSI 的一致性

沿着这个方向，可以进一步推到两个更大的命题。

第一个命题关于 AGI。实现 AGI 的关键，可以这样表述：**在 LLM 自身的概率图灵机族里，包含了一类能够根据输入进一步拓展图灵机族能力的子集；同时，存在一种方法，能找到这个子集隐式对应的 harness。**也就是说，模型内部本来就潜藏着"自我拓展"的可能，harness 的任务就是把这种可能找出来、固定下来、显式化。

第二个命题关于这种拓展能否在 harness 层实现。基于前面的讨论，答案是肯定的：**拓展图灵机族能力的那个子集，同样可以在 harness 层面实现。**我们不需要一直回到模型训练层去做这件事；很多时候，改 harness 的表达能力，就已经足够拓展机器的能力边界。

把这两个命题合起来，就得出一个贯穿全文的结论：**AGI 和 RSI（递归自我改进）在理论本质上是同一件事。**它们共同的内核，都是"系统能否持续拓展自己的能力边界"。区别只在于，这种拓展是藏在参数里，还是摆在 harness 产物里。而我们选择摆在 harness 里。

### 1.5 Coding 的本质：投影并确定化

最后落到我们最关心的任务上——让 agent 完成 coding 任务，本质上是在做什么？

**Coding，是在一个概率图灵机族里，投影出一个面向目标子问题的子概率图灵机，然后通过修改其中的概率权重，提高这个子图灵机的确定性，最终在合适的成本范围内把问题解决掉。**

这句话有几层含义。第一，我们不是凭空造一台新机器，而是在现有的概率图灵机族里"投影"出一个专门的子机器，让它只对付眼前这个任务。第二，这个子机器一开始是概率性的、不确定的，我们要做的是逐步提高它的确定性——让它从"可能做对"变成"稳定做对"。第三，这一切都发生在一个成本约束之内，因为概率收敛是有代价的。

**所以，coding 的完整过程，就是投影、确定化、控制在预算之内这三件事的循环。**

## 2. 演化的最小单元

上面讲的是"一台机器"怎么工作。这一节把镜头拉远，讲"一群机器"怎么演化。

### 2.1 自然选择与模型训练的一致性

自然选择和大模型训练之间，存在一种结构上的一致性。两者都是这样的过程：产生大量变化，用某种标准评价这些变化，留下好的、淘汰差的，然后让留下来的成果继续产生下一轮变化。

一致性不是巧合，而是因为**演化这件事，在抽象层面就是"变化—选择—保留"的循环。**自然选择里，变化来自基因突变，选择来自环境与繁殖，保留靠遗传；模型训练里，变化来自不同样本梯度，选择来自损失函数，保留靠权重更新。

### 2.2 微观与宏观的最小单元

确定了循环结构之后，接下来的问题是：演化的最小单元是什么？答案要分微观和宏观两层看。

**微观上，自然选择的最小演化单元是碱基对，大模型训练的最小演化单元是连接和权重。**它们是各自系统里最细的、可以被独立改变并被选择的单位。碱基对的变异改变生物的性状，连接和权重的调整改变模型的行为。

但微观单位成不了气候，真正决定演化方向的是宏观单位。**宏观上，自然选择的最小演化单元是种群，种群要去解决它所在生态位的问题。**个体生死是微观的，种群在生态位里是存续还是灭绝，才是演化的胜负手。

顺着这个逻辑推到底：**agent 对应的最小演化单元，应该是会话组；会话组要去解决它们所面向的那个问题。**单个会话只完成了问题和方案之间的几次往返，真正的"一个能力"，往往要跨越多次生成、运行、修正、验收，这些动作在会话组里才完整。

### 2.3 会话组为什么是演化单元

把会话组定为最小演化单元，是因为它正好对应"变化—选择—保留"的完整循环。一次会话产生的是变异——不同的方案、不同的代码、不同的契约。会话组内的运行和验收执行的是选择——哪些变异被接受，哪些被淘汰。而会话组沉淀下来的产物——记忆、契约、matrix 记录——承担的是保留，让这次演化的成果能够进入下一轮。

**从这个角度回看，能力其实就是"一个会话组在解决它的问题时，成功保留下来的那些东西"。**而要让能力持续积累，就得让会话组成为稳定、可回收、可复用的组织单位，而不是随时消失的临时对话。

## 3. 组织是核心

### 3.1 自动分组是最大的痛点

现在的 agent，普遍缺一种能力：**根据问题自动对会话乃至会话内容进行分组。**这是当前一个大的、需要提升的痛点。今天大部分会话是按时间顺序、按用户点击堆叠起来的，而不是按"它们是不是在解决同一个问题"聚到一起的。

其后果是双重的。一是计算经济性下降——解决同一个问题的上下文被分散在多个会话里，每次都要重复检索、重复交代背景。二是解决问题的能力下降——本该共享的经验和中间成果彼此隔离，无法在需要的时候被取用。

### 3.2 长上下文不是银弹

有人会把希望寄托在越来越长的上下文窗口上，认为只要窗口够大，把一切都塞进去，分组问题就消失了。**但长上下文不是银弹，而且很快就会碰到瓶颈。**窗口再大，也有注意力分配、检索噪声、调用成本和跨会话持久性的天花板；更重要的是，把东西堆在一起，不等于把它们组织在一起。

**组织不是"放得下"，而是"找得到、对得上、收得回"。**这三件事，任何一件都不能靠单纯扩大窗口解决。

### 3.3 归根到底是组织问题

所以，我们把一个判断直接亮出来：**如何分析问题、划分问题、解决问题，归根到底是组织问题。**一个 agent 能不能稳定地把大问题拆成小问题，拆完之后能不能各自解决、再合起来，解决的过程中产生了哪些东西、这些东西往哪里放、下次能不能复用——所有这些，都是组织的范畴，而不是模型参数能自动兜住的范畴。

### 3.4 从汇编层到接口层

既然组织是核心，就需要一个组织的方法。我们采取的方案是：**用领域驱动设计（DDD）的思想拆解问题，把解决问题的程序在"编译层面"上，从汇编层提升到接口层。**

这个说法的意思是：不要让 agent 从需求直接跳进逐行代码（那相当于在汇编层写程序），而是先识别领域边界、定义领域对象、约定接口契约，然后再组织实现。汇编层关心"这一行怎么写"，接口层关心"这个能力是什么、输入输出是什么、哪些能互相替换"。**编译层面抬高一档，组织和复用的粒度也随之抬高一档。**

### 3.5 领域是种群，会话是个体

这套组织方法，恰好和第二节的演化视角严丝合缝地接上了：**领域，就是种群；会话，就是个体。**领域承载一簇相关问题及其候选能力，相当于一个生态位里的种群；会话承担一次具体的问题求解，相当于种群里的一个个个体。

这一映射让我们对"分组"有了清晰的操作语义：**把一个会话分到哪个组，本质上是判断它属于哪个领域种群；而一个领域该不该存在，本质上是判断这个生态位有没有足够的、持续的问题需要被解决。**

## 4. 落到系统设计

前面的推导，最终要落成一套可运行的系统。我们的系统把"能力调整"从不可见的参数空间，搬到可见、可版本化、可复用的工程产物上。分工如下：

- **matrix** 承载执行与验收——它是会话组落地后的具体形态，也是接住概率收敛的确定性骨架。
- **domain** 承载问题边界与会话组——对应前文的领域种群。
- **model / stub / interact** 承载接口层契约——对应前文"编译层提升到接口层"。
- **导出 / 导入与能力检索** 承载能力的遗传与组合——对应前文的显式权重与演化保留。

### 4.1 一份元素一个根 matrix

每个 model、stub 或 interact 元素，都对应一个根 matrix。这个元素的实现、运行和验收，全部在这一个 matrix 内完成；子 matrix 承担进一步拆解后的执行，跨 matrix 的信息只通过明确的信箱传递。

**这样约束的用意，是给"个体"一个清晰的边界。**一个能力的实现、运行记录和验收结论，都收拢在同一个根 matrix 里，不会散落进多个会话无法回收。骨架 DAG 先锁定节点类型和 Cin/Cout，预构建再生成可执行的 definition——这一步就是前文说的"投影"，把一段概率性描述收敛成一个可执行的结构，然后靠运行和验收逐步提高它的确定性。

### 4.2 interact 依赖接口，不直接依赖持久化

一条关键规则：**interact 禁止直接使用 persist，允许使用 stub。**这意味着业务流程只依赖接口，不直接依赖存储实现，存储本身必须通过 stub 暴露的契约被访问。

这正是"汇编层到接口层"在规则层面的落实。业务关注的是"我需要什么能力"，而不是"这个能力内部怎么存、怎么取"。stub 先约定 request/response，业务根据契合约组合，具体实现可以在契约边界内自由变化——**接口层让复用成为可能，也把实现和流程之间的耦合切断了。**

### 4.3 能力以导出包为单位遗传

能力如何跨会话、跨领域传承？答案是**导出包**。领域导出包只包含 request/response model 和 stub 契约，不导出 persistence、interact、matrix 和运行数据。

这个取舍极其重要：**遗传的是"接口与能力边界"，而不是某次具体实现。**实现是易变的、绑环境的，接口却是稳定的、可复用的。导出包于是成为演化里的"遗传单位"——把稳定的接口传下去，把脆弱的实现留在原地，让新环境里重新长出适配的实现。

由此，能力形成了一条清晰的累积回路：

**能力导出 → 能力检索 → 导入 → 组合出新领域能力。**

探索出的能力进入导出包，导出包被检索并被复用到新问题上，新问题再产出新的导出包。**这是一条递归自我改进（RSI）的回路——系统通过不断导出、检索、导入，把自己已经具备的能力，变成未来解决更难问题的构件。**

### 4.4 用确定性校验压缩概率搜索

概率图灵机的泛化有代价，我们前面说过。对冲这个代价的办法，是把确定性校验织进流程：schema 校验、契约校验、门禁状态、验收。这些确定性检查，把无边界的概率搜索压缩成有栅栏的路径，减少无效的 LLM 调用，让概率机器的成本回到可控范围。

对应到分工上：**LLM 节点只负责真正需要判断和生成的那些环节**，把泛化交给模型；确定性控制、校验和审计交给 harness。两者各司其职，概率图灵机族的威力被保留，效率代价被压制。

## 5. 尚未展开的问题

这套设计给出一条完整的逻辑链，但也留下了几个必须正面回答的问题。

**会话组的自动分组判据是什么？**现在把需求归到哪个领域，还主要靠人工或 agent 判断。能否从需求文本自动判断"它应该属于哪个已有领域"，而不是每次都要人来建领域、人来分类？

**导出包要不要补充领域关键词和术语表？**能力检索的召回质量，很大程度取决于导出包里有没有足够的、可被命中的语义信息。关键词和术语表能否显著提升召回？

**能力检索的效果如何度量？**命中率、契约缺口识别准确率、导入后一次通过率——哪个才是衡量"检索对了没有"的正确标尺？

**RSI 回路的自动化边界在哪里？**能力检索到导入这条链路，哪些环节可以全自动，哪些必须人工确认？全自动的自我改进，和需要人在环上的自我改进，风险完全不同。

**领域之间是否也需要选择压力？**如果领域是种群，那么低复用的能力是不是该像不适应环境的个体一样被归档、被淘汰？让能力库保持活性，本身是不是也需要一套选择机制？

## 结语

我们从"LLM 不是图灵机、agent 才是"出发，到概率图灵机族，到后训练与 harness 的隐式/显式权重，到 AGI 与 RSI 的一致性，再到会话组作为演化最小单元，最后落到"组织是核心、接口层是入口、导出包是遗传单位"的系统设计。

这条链的每一步都指向同一个结论：**agent 的能力，是可以被当成工程产物来显式管理、组合和演化的。**真正稀缺的不是更强的模型，而是一套能让模型的能力被稳定组织、被确定性校验、被跨会话遗传的系统。这就是我们在做的事。
